# 2026-10-28 EDMA 源码修复与诊断补全

## 原因与改动

旧 AP 发送修补后，CMD_TX_DATA 状态拒绝没有新增，但真实内核日志仍出现 EDMA pending queue full、push link fail:-1、tx return err。持久过滤器漏采后两类和队列告警，所以单看原固件错误计数会漏报。分别记录为 R89 / R90，不覆盖先前的失败记录。

采用官方固定 v2026.10.27.2 的 5.4 Image / generic ramdisk 和 187 个配套模块；无线模块以相同配置 / Clang 12 源码重编译，保留 PCIe AP/GO ARP与普通DNS保护，官方 EDMA 补丁处理可重试压力与完成唤醒。rootfs 继续使用原版本，不覆盖面板、登录、统计与个人配置。源码与适用范围见[构建说明](../../extras/dashboard/optional/wifi-source-repair/README.md)。

过滤器保留 EDMA / TX 失败，BUG 使用词边界，避免把 DEBUG 误当崩溃上下文；同时识别大小写 Kernel panic。启动辅助脚本仅对特定厂商驱动跳过无效默认天线、距离0和自动功率命令，显式配置与其他驱动保留原行为。

## 三层检查

| 层级 | 结果 |
|---|---|
| 明显错误 | 官方签名清单与原包 SHA 验证；编译配置与发行 Image 一致；267 项导入 CRC、42 项导出、依赖与 CFI 核对；语法、包 SHA、安装映射与链接检查 |
| 状态与恢复逻辑 | 实际 ARM64 分类 776 项；EDMA 错误预算、成功重置、完成超时 / 空指针 / 唤醒一次等 523 项。辅助总线、锁、客户查询等明确使用桩，不冒充真实固件；隔离 updater 组装 / 整套模块同步 / 回退通过，真实 boot 与模块哈希未变 |
| 设备场景 | 用户确认后应用并正常重启；真实三轮局域网每方向64MiB与三轮蜂窝每方向2MiB，文件SHA一致，客户端上下行统计分别增加。启动辅助修正后再次正常重启复核；名称映射、设备集合、有效累计、管理配置与登录会话功能保留 |

13 项日志过滤场景各三轮通过，真实日志的新 EDMA / TX 错误已能持久保存；旧过滤器不能正确通过同一夹具。PHY 默认 / 显式 / 其他驱动144项隔离检查及补丁重复执行幂等检查通过。实际第二次启动的无效默认命令、powered-off CMD_SET_PARAM、-12 告警未再出现。

压力测试曾出现可重试队列 full 警告，但未再出现 push link fail / tx return err / 固件命令拒绝，实际数据校验通过；不能要求完全没有队列压力警告或以压掉日志代替修复。未见本轮新内核 OOM / Oops / panic 或存储 I/O 错误。DNS、HTTPS、AP、插件、采集正常，页面 HTTP200并签发既有免密规则的会话；未扩充名单或修改期限。

两次启动后的传输检查均通过；最后另做三轮每轮5个ARP往返、三轮A/AAAA客户端DNS查询。A正常回答，AAAA按照原策略返回无错误的空回答，不为测试改变IPv6配置。初次DNS夹具错误地要求AAAA也必须有答案，核对既有策略后修正断言重新测试，失败记录保留。名称映射逐字相同、设备集合不变，日/月/总累计不下降；新启动只重建速率基线。

旧日志脚本中的“oom”累计也包含netifd的命令返回 -12，不等于Linux OOM killer；本轮内存结论使用当前内核的真实OOM特征。SIPA -115通常为IPA恢复中的正常流控，不单独当作发送故障。回退的隔离测试不等于真实恢复演练；最终完整快照恢复脚本仅做目标、哈希和语法核对，没有为测试主动触发回写或断开唯一管理入口。

## 失败与限制

初次后台启动因设备没有 nohup 未执行，已核实当时没有写入，改用现有 setsid 后完成。交叉编译最初未正确携带架构选项，随后配置检查又发现两个链接测试项不同；补齐工具链后与官方配置逐字一致才接受产物，早期产物没有部署。回调隔离夹具最初未考虑 LTO 内联全局 HIF，修正夹具后重测，未把该失败归因为设备驱动。原始日志与私人备份不公开。

实际操作与原始证据保存在使用者私有材料；完整系统恢复演练、真实掉电、长期弱信号 / 热状态及运营商计费精度未完成。旧全量基线仍单独维护，不能据此次内核和模块更新宣称上游新版完整 OpenWrt 与所有页面都已实测。
