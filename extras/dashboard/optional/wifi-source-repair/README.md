# 官方 5.4 底座与源码无线修复

适用：已核对的 PCIe F50、厂商 5.4。源码补丁遵循 [GPL-2.0](LICENSE)，不包含内核、固件或 `.ko`，基础面板安装器不应用、不重启。

## 为什么需要这份源码补丁

官方 [v2026.10.27.2](https://github.com/dikeckaan/mu300-linux/releases/tag/v2026.10.27.2) 已含 EDMA 回压重试、完成回调唤醒、skb 头部、描述符前缀和 IPv6 组播修正。原局部二进制补丁没有覆盖 EDMA，实际仍出现 pending queue full、push link fail:-1 和 tx return err。

但该发行包的无线模块仍让部分 AP ARP 走命令队列。本补丁在官方补丁之后应用：只让 PCIe AP/GO 的 ARP 和普通 DNS 提前回到数据队列，保留其他模式、DHCP、VoWiFi和其他硬件的原分支；三处常规日志改为 debug，真实错误保留。

## 固定来源与构建

- mu300-linux：`fa7bd593c5da6bf7963164e5a274253c4705960f`。
- 内核来源：`Enceka/android_kernel_zte_ums9620_mifi_u30air`，提交 `b50db5b6224c11db42a246e8fcdaad1e1d59f478`。
- 无线模块来源：`realme-kernel-opensource/realme_C51_C53_Narzo-N53-AndroidT-kernel-source`，提交 `4381465ccaf87fcf3215b9cd42f4a685df40e5e0`。

在独立构建电脑上，使用上游固定提交的 `kernel/build-all.sh`、Dockerfile 和配置。将本目录 `wlan_combo-zz-f50-ap-dns-arp.patch` 复制到其 `kernel/patches/`；`zz` 保证它在该版本全部官方无线补丁之后应用。构建入口会重新检查补丁集并拒绝陈旧源树。完整内核重建按上游要求准备原生 ARM64 或相应构建环境，本轮没有运行这一完整重建流程。

本轮实际采用官方已签名发行包的 Image、generic ramdisk 和配套模块，仅交叉重编译无线模块：从发行 Image 提取配置，使用相同 Clang 12、固定内核和全部官方补丁准备头文件；从该发行模块集合核对版本 CRC，未知接口或冲突拒绝构建。生成模块与官方模块的 267 项导入 CRC、42 项导出和依赖相符，CFI 保留，配置逐字一致。构建记录与二进制保存在使用者私有材料，不把特定产物 SHA 当成所有编译环境的固定输出。

## 内核与模块必须一起处理

官方此版 5.4 tar 没有 `kernel.release`；现用旧 updater 的 `boot` 路径因此不会同步系统模块。只更新启动镜像不能视为驱动更新完成。应在验证过的本地暂存包中声明实际内核 release，并按清单安装完整模块集合、备份原集合；所有原始官方输入仍分别核对签名与 SHA，本地重新打包文件不能冒充原官方签名包。

本轮先在隔离目录执行真实 updater 的组装、模块同步和回退，将启动写入与 trial 操作替换为测试桩，确认真实分区未改变，再经用户确认应用。自动回退只覆盖其实现检查到的失败条件；保留电脑上的完整备份和独立恢复方法。更新保留 rootfs、面板、认证、名称映射与有效账本，不关闭加速，不重新套用网络或性能默认配置。

## 验收

776 项实际 ARM64 分类检查和 523 项错误预算 / 完成唤醒检查通过；硬件、锁、固件和时序部分使用明确的桩，不能替代设备测试。实际重启后完成三轮局域网与三轮蜂窝上下行及文件校验，分类统计增量正确。EDMA full 作为可重试压力可能仍出现，验收重点是无新增 push link fail / tx return err、数据正确及队列继续工作，不能靠静音全部警告宣称修复。

详细结果与未测范围见[本轮检查](../../../../docs/reviews/2026-10-28-edma-source-repair.md)。长期弱信号、断电和所有固件故障仍不能由短时验收排除。
